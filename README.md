# 一起开黑 · 游戏预约接龙

轻量级多人游戏组局平台：**创建预约 → 分享链接 → 昵称报名 → 满员可候补**，普通参与者无需注册。

- 支持创建、报名、退出、分享，以及发起人和管理员编辑、取消预约。
- 管理员支持回收站恢复预约；主管理员可创建、停用和重置其他管理员。
- 首页和管理员预约列表支持分页、搜索游戏名／发起人、状态及北京时间日期筛选；未过期预约优先。
- 服务端校验人数上限和昵称重复，通过数据库事务避免并发超员。
- 深色界面，适配手机与桌面；时间统一按北京时间（UTC+8）展示。

技术栈：Next.js 16、React 19、TypeScript、Tailwind CSS 4、shadcn/ui 风格组件、Zod、Prisma 6、SQLite。

## Docker 部署（推荐）

Linux 服务器需要 Docker Engine、Docker Compose v2 和 Git，无需安装 Node.js。以下命令使用 Bash。

```bash
git clone https://github.com/aloha1024/party-up.git
cd party-up

# 保留已有配置
[ -f .env ] || cp .env.example .env
chmod 600 .env

docker compose up -d --build
docker compose logs -f web
```

私有仓库需要先配置 GitHub 访问权限。启动后访问 `http://服务器IP:3001`，并放行对应端口。按 `Ctrl+C` 退出日志查看，网站继续在后台运行。

**首次启动会自动迁移数据库并初始化管理员。** 保持示例中的三项 `ADMIN_*` 变量为空，日志会输出账号 `admin` 和随机临时密码。保存密码后访问 `/admin`，首次登录必须设置正式密码。

`docker build` 只构建镜像；账号和密码在**首次启动的容器日志**中输出。已有管理员配置时会保留密码，不重新生成。

### 修改端口

在项目的 `.env` 中设置：

```dotenv
APP_PORT=8080
```

然后执行 `docker compose up -d`，通过 `http://服务器IP:8080` 访问。默认宿主机端口为 3001，容器内部端口为 3000。

## 浏览与筛选

首页和管理员预约列表默认每页 12 场，未过期预约按时间从早到晚排列，已过期预约排在后面。可按游戏名／发起人搜索，组合筛选开玩日期和状态：全部、未开始（含满员）、有空位（未开始）、已开始、已取消。筛选条件和页码保存在 URL 中，支持分享和浏览器前进／后退。

预约详情在可见且联网时约每 15 秒自动更新。首页、管理员预约列表及回收站从 15 秒开始，成功刷新且数据未变化时逐步延长到 30、60 秒；发现变化、切换筛选／页码或完成操作后恢复短间隔。各次等待加入最多提前 10% 的随机偏移以分散请求，不会超过所选间隔；失败不会被当作“数据未变化”。切回页面或恢复网络时会尝试立即刷新，可见预约到开玩时间时也会唤醒刷新。隐藏、离线、刷新进行中及报名、退出、候补加入／退出、取消、后台删除和恢复操作期间暂停自动请求；输入中的昵称与滚动位置保留。时间间隔指请求之间的调度等待，不包含网络及服务器处理耗时。

列表接口 `GET /api/reservations` 支持 `q`、`view`、`date`、`page`、`pageSize` 参数。`view` 可选 `all/upcoming/available/started/ended/cancelled`，`date` 为北京时间的 `YYYY-MM-DD`；每页最多 48 场。**返回格式改为分页对象**：`data.items` 为预约摘要（包含 `participantCount`），另有 `total/page/pageSize/pageCount/filters`。列表不再返回完整报名名单；名单仍通过预约详情接口获取。非法筛选参数返回 400，超过实际页数会显示最后一页。

预约状态增加“有空位（未开始）”，大厅、我的预约及后台预约列表均可使用。只显示未删除、未取消、未开始且报名人数少于上限的预约；已经报名的预约仍会保留。报名中的预约显示“还可报名 N 人”，人数包含发起人。空位以提交时为准，列表展示不占位；满员、退出、扩容后的变化随自动刷新更新。搜索、日期和分页可以与该筛选组合使用。

### 我的预约

顶部“我的预约”进入独立页面，默认显示“我参加的”，可切换“我发起的”和“我候补的”。自己发起且仍在报名名单中的预约会同时出现在前两个分类；退出后仍可在“我发起的”中找到。候补递补成功后转入“我参加的”。已开始或已取消的候补记录仍可查询，移入回收站后隐藏，恢复后重新显示。

支持搜索、状态、北京时间日期筛选和分页，分类切换保留筛选并返回第一页，重置筛选保留分类。沿用列表 15 → 30 → 60 秒自适应刷新。

无需注册，仅显示当前浏览器身份对应的记录。换设备或清除浏览器数据后无法找回；缺少身份时显示空列表，不会自动创建身份。管理员也只看到当前浏览器对应的记录。

### 再开一局

在自己的预约详情页点击“再开一局”，复制游戏名称、发起人昵称、人数上限和备注，再重新选择日期和时间。报名中、满员、已开始及已取消的预约均可使用；已移入回收站的预约不可使用。仅原发起人的浏览器身份有权读取模板，管理员身份不额外获得此权限。

提交后生成新的预约和分享链接，当前发起人自动占一个名额，正式名单和候补名单均不会复制，旧预约保持不变。配置以打开复制页面时读取的内容为准，来源后续修改不会同步。

已有创建草稿时，可选择恢复旧草稿（含原填写的日期时间），或丢弃后使用本次配置；打开页面不会自动覆盖草稿。未确认的创建记录仍可查询结果，内容不同不能替换原提交编号，也不会自动重发。无数据库迁移或额外配置。

### 候补队列与自动递补

未开始、未取消且满员的预约可主动点击“加入候补”，每场最多 100 人；普通报名失败不会自动加入候补。候补昵称和顺序公开，详情页会显示本人当前位置，分享文字也会单列候补人数和名单。候补不是正式报名，不计入列表人数或占用正式名额。

正式参与者退出或发起人／管理员增加名额时，按入队顺序自动递补至满员。普通报名不能插队，昵称和浏览器身份在两份名单之间也不能重复。退出候补再加入会排到队尾；若退出时已递补成功，页面会提示刷新后退出正式接龙。加入候补时若已经有空位，会提示直接报名。

开局或取消后停止递补，保留候补记录并显示“未递补”或“预约已取消”，本人仍可退出候补。回收站保留队列，恢复未来且未取消的预约时补齐空位，永久删除时清理。**不发送外部通知**，请主动查看详情或“我的预约”；详情自动刷新会更新候补／正式报名状态，断网或请求失败后先刷新确认结果。

新增 `POST /api/reservations/[id]/waitlist`（`{ "name": "昵称" }`）与同路径 `DELETE`（退出本浏览器的候补），沿用身份 Cookie、同源检查、报名限流和请求预算。详情响应的 `waitlist` 仅含公开编号、昵称、入队时间和 `isMe`；`participants` 仍只包含正式名单。个人列表使用 `tab=waiting`，其余筛选及分页规则不变。

本次新增 `20260926000100_waitlist` 数据库迁移；旧预约候补初始为空，原预约、报名、管理员和创建提交记录保留。**更新前先备份**，再通过现有 Docker 启动流程自动迁移，无新增环境变量。备份格式不变，校验器按已完成迁移检查候补表，仍接受迁移前备份。**回退旧代码必须同时恢复迁移前备份，不能让旧代码继续写入带候补的新数据库。**

### 添加到个人日历

未开始、未取消预约的正式参与者，可在详情页点击“添加到日历”，再点击“下载日历文件”，用个人日历应用导入 `.ics` 文件。发起人退出正式名单后不能导出，管理员无额外权限；候补者递补成功后可使用。每次准备文件都会重新核对身份并读取最新预约，导出不会改变报名状态。

文件包含游戏名称、发起人、备注、开玩时间和详情链接，不包含正式名单、候补名单或浏览器身份。使用 [iCalendar（RFC 5545）](https://www.rfc-editor.org/rfc/rfc5545.txt) 格式，以 UTC 记录实际时间，日历应用按自己的时区显示。项目没有结束时间，因此不指定结束时间；默认附带提前 15 分钟提醒，实际是否提醒及提醒方式由日历应用决定。

**这是一次性副本，不会自动同步。** 预约修改、取消或本人退出后，请手动调整日历；重复导入可能产生重复事件。下载成功仅表示文件已保存，不代表已导入或一定收到提醒。本轮不连接外部账号或通知平台，不增加数据库迁移、环境变量和依赖，部署沿用现有更新流程。

新增只读接口 `GET /api/reservations/[id]/calendar`，返回生成日历所需的最新预约字段，复用现有 JSON 日志与请求预算，不缓存个人响应。接口仅认当前浏览器身份，不接受 URL 中指定用户；文件及详情链接由浏览器使用当前站点地址生成。

### 到场确认与结束状态

正式参与者（含仍在正式名单中的发起人）可从开局前 30 分钟开始，确认或撤销本人的到场；开局后仍可补确认，预约取消或结束后锁定。候补和未报名管理员不能确认或代签到。有详情权限的访客可查看到场人数及北京时间确认时间；“未确认”不代表缺席，邀请预约仍需对应查看权限。

修改开玩时间会清空已有到场确认，编辑页会提前提示；只修改其他内容不会清空。退出或被移除后再次报名、候补递补均从未确认开始。到场操作不改变报名时间、名额、预约编辑版本，也不写公开变更历史。

发起人或有效管理员可在开局后点击“结束预约”，再通过“撤销结束”恢复为已开始；两者均保留已有到场记录并写入公开变更记录，管理员操作同时进入审计。结束后不能报名、编辑、取消、改名、移除或递补，候补仍可本人退出。“再开一局”生成全新预约，不复制到场或结束数据。不会按预计时长自动结束，旧预约也不会自动补填结束时间。

大厅、我的预约、后台及列表 API 支持 `view=ended`；`view=started` 现在表示“已开始（未结束）”。公开分享文字反映结束状态，不附到场名单或确认时间；邀请分享不变，已结束预约不能添加日历。详情沿用自动刷新，在到场窗口开放时唤醒；操作期间暂停自动刷新，离线或响应丢失时先刷新核对，不自动重发。

新增 `PATCH /api/reservations/[id]/attendance`，接收 `participantId`、`checkedIn`、`attendanceVersion`、`editVersion`；新增同预约的 `/completion`，`POST` 结束、`DELETE` 撤销，均接收 `editVersion`。接口返回最新详情，版本过期返回 409；服务端独立检查身份、权限、状态与时间窗口。只保存本人当前到场状态，不新增缺席处罚或通知。

升级前备份数据库及配套密钥，启动时自动迁移新增字段。备份格式不变，旧备份仍可恢复；软删除和恢复保留到场及结束状态，永久删除清理报名数据。回退旧代码须恢复升级前备份。

### 邀请制预约

创建时可选择“公开预约／邀请制预约”，默认公开，创建后不能切换。旧预约全部保持公开。邀请预约不会出现在公共大厅、搜索结果、统计或公共列表 API；后台可管理全部预约，“我的预约”按发起、参加或候补关系显示。

发起人或有效管理员在详情页点击“分享邀请”获取链接；持链接者点击“接受邀请并查看”后才取得当前浏览器的访问权限，不会自动报名。链接可转发，不绑定指定人员。邀请凭据位于 `#invite=` 片段中，页面读取后移除地址栏片段，只在组件内存中暂存；刷新尚未接受的入口时需重新打开原链接。分享仅附邀请提示与链接，不附备注或名单，日历也不携带凭据。

“更换邀请链接”会使旧链接及尚未加入者的旧授权失效。正式参与者、候补及曾加入者保留查看权；退出或被移除后也能查看本人移除原因。重新加入需要当前有效邀请授权，发起人例外；管理员身份本身不能代替报名邀请。更换响应丢失时先重新获取链接确认结果，不自动再次更换。“再开一局”保留可见性选择，但生成独立邀请和授权。

授权仅关联浏览器身份，换设备或清除 Cookie 后无法恢复。未授权详情只显示邀请入口，相关读取接口返回 404；自动刷新确认失去权限后清除详情和已加载历史。软删除期间不可访问，恢复后保留原邀请版本，永久删除清理授权。没有逐人审批或外部通知。

邀请凭据以摘要校验，原文使用现有 `ADMIN_SESSION_SECRET` 经 AES-256-GCM 加密保存。Docker 自动初始化生成的密钥保存在数据卷 `admin-bootstrap.json`；手工配置则保留相应 `.env`。**必须将数据库与配套服务器密钥一同备份和恢复，不要随意更换该密钥**，否则旧邀请无法再次读取。密钥缺失或无效时邀请创建明确失败，公开预约不受影响。

升级前先备份，由现有容器启动流程应用新增迁移；备份格式不变，校验器仍接受迁移前备份。**回退旧代码必须恢复升级前数据库备份，不能让旧代码读取或写入含邀请预约的新数据库，否则可能公开私密预约。**

### 报名信息管理

未开始且未取消的预约中，正式参与者和候补者可在自己的名单旁点击“修改昵称”，无需退出重新加入，不改变报名时间或候补顺序。昵称沿用原有长度和标准化规则，不能与任一名单中的其他人重名。发起人修改本人名单昵称时同步预约上的发起人昵称，增加编辑版本，并在公开变更记录中仅标记昵称已修改；其他人的改名不写入公开历史，也不保存旧昵称。

发起人和有效管理员可点击其他成员旁的“移除”，填写 1–300 字原因并确认；不能移除发起人或自己，本人仍使用退出入口。移除正式参与者会在同一事务中按候补顺序递补，移除候补不改变其他人的相对顺序。被移除者仍可重新报名或候补，原位置不保留；本功能不提供封禁或外部通知。

详情页的“报名移除记录”仅展示当前浏览器有权查看的内容：发起人及有效管理员查看本场全部记录，其他人只查看自己被移除的记录，无记录时隐藏区域。记录按编号倒序、北京时间展示，支持分页和详情自动刷新；重新加入不清除记录。原因不出现在公开变更记录、分享或日历中。换浏览器或清除身份 Cookie 后，普通参与者无法找回原身份下的私密记录。

正式报名和候补接口新增 `PATCH`，请求包含字符串 `entryId`、`expectedName` 和新 `name`。新增 `POST /api/reservations/[id]/roster-removals`，请求包含 `kind`（`participants` 或 `waitlist`）、字符串 `entryId`、`expectedName` 和 `reason`。服务器按浏览器身份或已验证管理员权限操作；过期记录、改名或递补冲突要求刷新确认。重复移除原记录不会再次操作，也不会误删重新加入的记录。响应丢失时不自动重发，请先刷新确认。

同路径 `GET` 返回 `{ data: { items, nextBefore } }`，固定每批 10 条，支持 `before` 游标；权限范围在数据库分页前应用。浏览器加载更多时使用服务器生成的、不含身份信息的查看范围标记 `scope`，权限变化后清空已加载记录并刷新。详情两份名单新增 `isHost` 标记；所有接口保持不缓存，不返回身份摘要，不记录昵称和原因正文到请求日志。管理员移除另写入现有管理员审计。

新增迁移 `20260926000300_roster_management`，保留原有预约、报名、候补、变更历史和管理员数据。私密移除记录包含当时昵称和原因，软删除后不可访问，恢复后可见，永久删除级联清理；“再开一局”不复制这些记录。**升级前先备份**，由现有 Docker 启动流程迁移，无新增依赖或配置。备份格式不变，按已完成迁移检查新表，旧备份仍可恢复；**回退旧版本应恢复升级前备份**。

### 预约变更记录

详情页公开展示最新 10 条变更记录，可点击“加载更早记录”。记录按编号倒序排列，时间显示为北京时间；沿用详情页自动刷新，补齐刷新期间新增的记录后与已加载历史合并。加载失败保留原有内容并提供重试，不另设轮询或通知。

每次有效编辑合并为一条记录：开玩时间和人数上限显示前后值，游戏名称、发起人昵称、备注只显示“已修改”，不保存这些字段的历史内容。取消仅记录“预约已取消”，原因查看当前详情。操作者只显示“发起人”或“管理员”，不公开管理员账号或浏览器身份。无变化提交不生成记录；创建、报名、退出、候补递补、删除和恢复不记入此历史。

只读接口 `GET /api/reservations/[id]/history` 返回 `{ data: { items, nextBefore } }`，固定每批 10 条；将 `nextBefore` 作为下次请求的 `before` 获取更早内容。游标必须是单个有效的正整数记录编号，非法或重复参数返回 400。无需身份，不创建身份 Cookie，响应不缓存；不存在或已移入回收站的预约返回 404。现有详情 API、分享文字和日历文件不追加历史。

新增迁移 `20260926000200_reservation_history`，不回填旧记录；旧预约初始显示“暂无变更记录，仅记录功能启用后的修改”。编辑、递补、审计和历史写入在同一事务内，失败整体回滚。回收站保留历史，恢复后可见，永久删除级联清理；“再开一局”不复制历史。

**升级前先备份**，再按现有 Docker 更新流程启动并自动迁移，无新增依赖或环境配置。备份格式保持不变，校验器根据已完成迁移要求历史表，仍接受迁移前备份。**回退旧版本时恢复升级前备份**，避免旧代码写入造成历史缺口。

Docker 启动时自动应用数据库迁移，升级保留现有预约、管理员和密码。初始化和命令行重置脚本只管理原始 admin 账号。

### 操作记录

已登录且启用的管理员可在 `/admin/audit` 查看管理操作，按管理员、对象名称／ID 或操作类型筛选，每页 20 条，按时间倒序排列。记录包含操作人、操作类型、对象及北京时间（精确到秒）。

仅从功能启用后开始记录，不补录旧历史；普通发起人的操作、登录尝试、Docker 初始化和命令行重置不在记录范围内。不保存密码、密码哈希、会话密钥、报名身份凭据、备注或取消原因。记录随数据库一起备份和恢复，网站不提供修改／删除记录的入口。

### 使用 GHCR 中已验证的镜像

`main` 每次推送通过全部检查后，CI 会将**同一个已测试镜像**发布到 `ghcr.io/aloha1024/party-up`。发布任务不重新构建，先核对镜像 ID、提交版本及运行版本，推送后再按摘要拉取核对。Pull Request 和手动检查不会发布。

- 提交标签：`ghcr.io/aloha1024/party-up:sha-完整40位提交号`。
- 推荐部署：使用该次 Actions 的 **publish → Summary** 输出的 `ghcr.io/aloha1024/party-up@sha256:完整摘要`。提交标签可被重推，摘要固定镜像内容。
- 自动发布使用 GitHub 提供的 `GITHUB_TOKEN`，只有 publish 任务拥有 `packages: write`，无需配置额外发布密码。
- 首次 GHCR 包默认私有。服务器拉取私有镜像时先执行 `docker login ghcr.io -u aloha1024`，在密码提示中输入具有 `read:packages` 权限的 classic PAT。包设为 public 后才支持匿名拉取，发布流程不修改包可见性。参考 [GitHub 包权限说明](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility)。

首次从源码部署切换时，先在原项目目录按原配置运行 `bash scripts/backup.sh backup`，再在原 `.env` 中设置（将摘要替换为该次发布的实际值）：

```dotenv
COMPOSE_FILE=compose.image.yaml
PARTY_IMAGE=ghcr.io/aloha1024/party-up@sha256:完整摘要
```

`compose.image.yaml` 是独立配置，不与 `compose.yaml` 叠加。它沿用同一项目的 `reservation-data` 卷；必须保持原目录或原来的 `-p` 项目名。设置后执行：

```bash
docker compose pull web
docker compose up -d --no-build --wait web
```

后续更新先确认目标发布已成功，**保留旧镜像和旧的 `PARTY_IMAGE`，在修改 `.env` 前备份**，然后替换为新摘要，拉取并启动。当前 CI 只构建 Linux amd64 镜像。

候选镜像仍以 `tested-container` 构建产物保留 1 天，包含 `candidate-image.tar` 和 `candidate-image-id.txt`，可用于排查发布问题。超过保留期后，应重新运行完整检查流程；仅重跑 publish 无法取得已过期产物。

回退分两种情况：

- **没有不兼容的数据库迁移**：将 `PARTY_IMAGE` 改回保留的旧版本，再启动并等待健康检查。
- **数据库也需要回退**：停止更新操作，按下面的恢复流程使用升级前快照；快照会同时恢复当时 `.env`，因此要保留对应旧镜像和兼容的 Compose 配置。恢复会丢弃快照之后的数据，脚本会先保存恢复前快照。

不要直接让旧代码运行在不兼容的新数据库上。备份中的版本和迁移清单用于核对，不能自动证明任意两个版本兼容。

### 备份与恢复

在 Linux 服务器的项目目录执行（需要已构建的镜像和 `flock`，通常由 `util-linux` 提供）：

```bash
# 自动停止网站、备份并校验，然后恢复原来的运行状态
bash scripts/backup.sh backup

# 检查指定备份；将路径替换为实际生成的目录
bash scripts/backup.sh verify backups/backup-实际目录名

# 覆盖当前数据前，自动生成 pre-restore-* 恢复前快照
bash scripts/backup.sh restore backups/backup-实际目录名 --confirm
```

备份包含预约、正式报名、候补队列、管理员密码哈希、会话密钥及服务器 `.env`；使用文件校验值、SQLite 完整性和外键检查验证。新备份的 manifest v2 记录执行备份工具的应用／镜像版本，以及数据库实际已应用的迁移和校验值；旧版 v1 备份仍可恢复。默认放在 `backups/`，仅保留最近 7 份常规备份；恢复前快照不会自动清理。可通过 `BACKUP_DIR=/安全路径 KEEP_BACKUPS=14 bash scripts/backup.sh backup` 调整目录与数量。

恢复会同时恢复 `.env`，因此端口和管理员配置也会回到备份时的值。使用生成备份时的代码版本，或已确认兼容的新版本恢复；在原 Compose 项目名和数据卷下执行。备份和恢复期间网站会短暂停止，原本已停止的网站不会自动启动。恢复中途失败时网站保持停止，请根据提示使用恢复前快照处理后再启动。原本运行的网站在备份后重启、恢复后启动时，脚本会等待 Docker 健康检查通过；启动失败返回非零并尝试停止网站，明确区分“数据已恢复”和“网站可用”。默认等待 120 秒，可设置 `WEB_HEALTH_TIMEOUT=180`（1–600 秒）。

备份目录仅限当前系统用户访问。请另外保存一份到其他磁盘或服务器；不要将配置、数据库或备份提交到 GitHub。

`docker compose down` 会保留数据卷；**`docker compose down -v` 会删除数据**。SQLite 部署保持单个网站实例；公网访问应配置 HTTPS。

## 定时备份与本机健康检查（Linux systemd）

在已部署的原项目目录中执行。需要运行 systemd 的 Linux、Docker Compose v2、util-linux（`flock`、`runuser`）及 coreutils（`timeout`）。指定的部署用户需要能访问项目、读取 `.env` 并连接 Docker；请使用平时执行备份的同一个用户，避免状态文件权限冲突。

```bash
# 安装；固定当前项目绝对路径，支持路径中的空格
sudo bash scripts/maintenance-systemd.sh install "$(id -un)"

# 查看下一次运行时间与最近状态（记录时间为 UTC）
bash scripts/maintenance-systemd.sh status

# 手动触发一次备份；会短暂停站，并等待完成
sudo systemctl start party-up-backup.service

# 查看备份与健康状态变化日志
sudo journalctl -u party-up-backup.service -u party-up-health.service --since today

# 暂停定时任务；不会中断正在执行的备份
sudo systemctl disable --now party-up-backup.timer party-up-health.timer

# 重新启用
sudo systemctl enable --now party-up-backup.timer party-up-health.timer

# 卸载定时任务；保留网站、配置、状态、数据库及备份
sudo bash scripts/maintenance-systemd.sh uninstall
```

每日 **北京时间 04:00** 自动运行现有备份脚本，默认保留最近 7 份常规备份，恢复前快照不自动清理。服务器错过执行时间不会开机补跑。沿用现有停站、校验和恢复运行流程；原本已停止的网站不会被启动。每台服务器这套安装命令仅管理一个项目，遇到同名但属于其他项目的单元会拒绝覆盖。

每分钟检查一次 Docker 容器健康状态，只记录状态变化，不自动重启网站。备份、恢复与检查共用 `.backup.lock`，维护期间跳过检查，结束后由下一次检查更新状态。Docker 查询有超时限制；连续相同故障不会重复输出日志，恢复会记录一次。健康检查进程执行成功不代表网站健康，请查看状态文件或日志中的 `status`。

`.maintenance/backup` 保存 `last_attempt`、`last_success` 和 `status`；`last_success` 仅在备份及原服务运行状态恢复都成功后更新。`.maintenance/health` 保存检查时间与健康状态。状态目录权限为 700，文件为 600，不提交到 Git、不打包进镜像。`running` 长时间未更新可能是维护仍在执行或进程意外终止，请结合 `systemctl status party-up-backup.service` 和日志排查；不要直接删除锁文件。安装单元权限为 600，不包含管理员凭据。

定时任务不继承交互终端的 `BACKUP_DIR` / `KEEP_BACKUPS`。需要调整时执行 `sudo systemctl edit party-up-backup.service`，添加：

```ini
[Service]
Environment="KEEP_BACKUPS=14"
Environment="BACKUP_DIR=/安全路径/party-up-backups"
```

确保部署用户可写该目录。卸载会保留自定义 systemd drop-in 配置，重新安装时继续生效。安装/升级工具前后可用 `systemctl cat party-up-backup.service` 核对配置；迁移项目目录前先从原目录卸载，再从新目录安装。

**当前未启用异地备份或外部通知。** 本机检查无法发现整机离线，本机备份无法防护整盘损坏；当前仅提供本机状态与 journal 日志。

## 创建防重复与报名身份

浏览器在创建、报名前先确认身份 Cookie 已保存，再提交业务请求。相同浏览器、相同提交编号的创建请求只生成一场预约；网络响应丢失后，在同一标签页用相同内容重试会返回原预约。成功后会清除编号，再次主动创建会生成新预约。标签页暂存本次创建内容与编号，成功或关闭标签页后清理；禁用标签页存储时只支持本页内重试。结果尚未确认时，修改表单内容不会替换原提交编号；可先查看结果或明确放弃记录。支持 Web Locks 的浏览器使用跨标签页锁协调首次初始化；普通 HTTP 等不支持该能力的环境使用 IndexedDB 事务协调，不在 IndexedDB 保存身份凭据。首次初始化时若两种协调方式均不可用，会明确提示允许存储或改用 HTTPS；已有身份仍可使用。

清除 Cookie 或换浏览器仍会失去原报名身份。已经删除的预约不会因重试而重新出现；数据库保留创建请求摘要用于识别旧请求，不自动清理。

外部 API 调用需先 `POST /api/identity` 保存 Cookie，再通过 `GET /api/identity` 确认 `data.ready`。公开预约写入缺少身份返回 428。创建时还必须提供 `Idempotency-Key` 请求头（16–100 位字母、数字、下划线或连字符），同编号内容不一致返回 409。重放返回当前预约信息，不重新报名。

## 草稿与创建结果恢复

创建和编辑表单在输入时保存当前标签页的草稿，刷新后可选择恢复或丢弃。草稿不会上传服务器，关闭标签页后结束保存；禁止标签页存储时会显示提示。编辑草稿保留原信息版本，预约已被其他人修改时只能查看旧草稿并手动选择需要的内容，不能直接覆盖最新版本。

创建超时或响应丢失后，点击“查看上次创建结果”即可找回原预约，即使开玩时间已经过去也可查询。查询使用原浏览器身份和提交编号；清除 Cookie 后不能据此恢复身份。确认找到结果或创建成功后清理草稿与提交编号。放弃未确认记录后再次创建可能生成另一场预约，界面会先提醒。

接口：`GET /api/reservations/submission` 携带原 Cookie 和 `Idempotency-Key`，返回 `data.state`：`found`（包含预约 ID、游戏名、时间）、`missing` 或 `removed`；不会返回其他浏览器的创建结果。

## 访问保护与超时

- 请求体限制为 16 KiB，按 UTF-8 字节流读取；超限返回 413，接收超过 2 秒返回 408。
- 管理员登录每账号每分钟 20 次，全站 120 次；可信代理来源另限每分钟 30 次。首次改密也计入登录尝试。
- 每浏览器每分钟：创建 10 次、报名／退出 30 次、管理操作 60 次。另有全站与可选来源上限，限流返回 429 和 `Retry-After` 等待秒数。
- 限流为单实例有容量上限的内存实现，进程重启会重置；不能当作多实例共享限流。
- SQLite 应用连接池固定为 1，事务先在连接池排队，避免少核机器上的引擎线程阻塞；数据库锁仍负责跨连接的一致性。服务端为请求分配 10 秒预算，写事务最多使用其中 8 秒，单次排队最多 1 秒、事务执行最多 3 秒、最多 3 次尝试。只重试可回滚的事务冲突；前端 15 秒超时后仍须核对结果。

默认 `TRUST_PROXY=0`，忽略客户端发送的来源地址头。只有在反向代理覆盖 `X-Real-IP`、正确传递 Host／协议，并阻止客户端直接访问容器端口时，才设置 `TRUST_PROXY=1`。直接通过 IP 访问无需开启。上线仍建议使用 HTTPS。

## 运行诊断与管理员会话

- 业务 API 返回 `X-Request-ID`；错误响应同时含 `requestId`，界面显示错误编号。服务器 JSON 日志记录编号、接口模板、状态、错误代码和耗时，不记录 Cookie、密码、请求正文或异常原文。
- Compose 使用 `local` 日志驱动，每个容器最多保留 3 个 10 MB 文件。查看最近日志：`docker compose logs --tail=100 web`。
- 每个业务 API 请求只写一条完成日志。`slow` 表示是否达到慢请求阈值，默认 1000 毫秒；`.env` 的 `SLOW_REQUEST_MS` 接受 100–60000 的整数，非法值回退默认值。成功但慢的请求使用 warning 级别。修改环境变量后需执行 `docker compose up -d` 重新创建容器。
- `transactionAttempts`、`transactionRetries`、`transactionMs`、`busy` 分别记录本次请求的事务调用次数、写事务重试次数、事务调用累计耗时以及是否耗尽预算／重试而繁忙。事务耗时包含排队和执行，不能据此分离数据库锁等待；普通非事务查询不计入该耗时。
- 未知错误附带 `errorType`、`version`、`errorFingerprint`，以及能够安全识别时的 `errorLocation`。位置仅包含白名单源码或构建文件的相对路径与行列号；不记录异常原文、完整堆栈、SQL、凭据或绝对路径。这些字段仅在服务器日志中，同一指纹便于聚类但不能证明根因相同；无法取得安全位置时仅按版本与错误类别聚类。
- 诊断覆盖统一响应封装的业务 API；Next 页面渲染／自动刷新请求及健康接口不属于该日志范围。没有新增外部监控或告警服务。
- 管理员页面底部显示运行提交；源码构建时传 `--build-arg APP_VERSION="$(git rev-parse HEAD)"`。容器中运行 `node scripts/build-info.mjs --json` 可查看构建和维护工具版本。
- “修改密码”页面新增“退出所有设备”，撤销当前账号的全部已有会话，包括本设备；其他管理员不受影响，并写入操作记录。普通“退出登录”仍只清除本浏览器登录。

docker compose logs --no-color --no-log-prefix --tail=1000 web | grep '"slow":true'
docker compose logs --no-color --no-log-prefix --tail=1000 web | grep '"busy":true'
docker compose logs --no-color --no-log-prefix --tail=1000 web | grep -E '"transactionRetries":[1-9]'

# 将实际错误编号／指纹替换进命令，定位同次请求或同类错误

## 多人编辑保护

发起人与管理员编辑预约时，会携带打开表单时的信息版本。若其他人已保存修改，旧表单会收到冲突提示，不能覆盖新内容；当前输入会保留，可先在新窗口查看最新预约。重新加载后可查看原版本草稿，复制需要保留的内容，再基于最新信息修改。

报名和退出不会改变信息版本；保存时仍按最新名单校验人数上限和昵称。此更新新增数据库迁移，旧预约版本自动初始化为 0，原链接、报名和管理员数据保留。Docker 启动会自动迁移，本地开发运行 `npm run db:migrate`。

接口变更：预约详情新增 `editVersion`；`PATCH /api/reservations/[id]` 必须携带详情中的 `editVersion`（非负整数）。缺少或格式错误返回 400，版本过期返回 409 和 `EDIT_CONFLICT`。成功保存后版本加一，冲突时业务数据和操作记录均不写入。

## 请求与异常恢复

创建、编辑、接龙及管理员操作统一设置 15 秒请求超时。网络中断、超时或代理返回错误页面时显示中文提示，并结束按钮等待；已提交的操作不会自动重试，因为服务器可能已经处理成功，请先刷新确认结果。创建或修改表单遇到请求错误时保留当前输入。

页面加载失败可点击“重新加载”重新获取服务端数据。管理员页面有独立的加载和错误提示。
